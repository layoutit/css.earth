# Billboard-first startup

A default object page with a prepared arrival billboard sends that image instead of the detailed scene DOM. It omits the old startup texture preloads. The renderer reads the full prepared object transport because there are no server-rendered scene nodes to adopt.

The shared responsive fit determines the initial silhouette. The camera retains the billboard's baked distance and rotation, adjusting projection scale to fit the viewport. The billboard and detailed scene therefore use the same perspective. Preparation requests the selected viewport texture level and uses the same visible-face demand as the mounted scene; existing low-resolution textures for unseen faces remain an independent resource optimization.

`site/prepared-arrival.mts` owns the resource lease, viewport texture policy, progressive mount options, camera acknowledgement, cancellation and cover release for startup and navigation. Startup supplies its prepared destination view; fly-to supplies its travelling camera and resumes its existing flight after acknowledgement. Both use the same scene-session activation and camera-acknowledged reveal path. The two modes differ only in camera progression: startup supplies a stationary destination; fly-to runs the existing travel clock.

The input surface stays inert through prepared scene activation, whether or not the camera can use a billboard cover. Like a fly-to replacement, startup attaches the shared world before mounting detail. Behind the photograph, startup builds that world and the shell while the first view's images download. On every screen a body first draws its first texture level, then sharpens to the level its size on screen calls for. The world's first frame is planned while the detail activates and paints: as soon as the detail's navigation facts exist, the world selects the body and plans the startup camera the detail already holds (`world-frame-queue.ts` `warm`). The plan is used only by the first request for that identical view while the world's presentation is unchanged, so the detail's connection commits it without planning again and the arrival's camera acknowledgement rides the same frame; any other request, a changed camera or a changed presentation plans as before. A change nobody owns yet (the caption's measurement) follows the committed frame with one more plan, as a refresh during a plan does. Both arrivals reveal at the proven fly-to boundary: activation has finished mounting and painting, and the destination camera publication has been acknowledged. The travel owner positions the cover during flight; attachment holds that image still until reveal. The cover does not subscribe to stage-coordinate camera publications. There is no extra router publication or second reveal gate. Readiness has no fixed delay. The small indeterminate loading line animates only its own transform and is removed at completion or failure. Reduced motion makes the line static. There is no startup coast, fade or second zoom.

Saved cameras enter the same preparation transaction before attachment. Static pages read the camera from the URL; server-rendered focus responses supply their resolved camera. Both resolve texture demand using the saved pose and projection scale. Preparation and mounting share one reader for the transported dataset and native settings. Paced activation consumes the baked groups even without a photographic cover.

Saved cameras, alternate datasets, feature links and system/overview links do not use the default photograph. Their scene stays hidden until the requested view is restored. Objects without a prepared billboard retain their existing server scene. Without JavaScript, the prepared billboard remains a static illustration.

`site/test/startup-billboard.test.mts` covers saved-view eligibility and the prepared perspective/texture selection at phone, tablet and desktop sizes. Real-device verification uses `--cold-load` with native screenshots; inspect the response sources and filmstrip, not just the capture's HTTP statuses.

The normal camera frame presenter preserves the stage offset used by world labels; arrival does not overwrite it with camera-root optics. Selected mesh captions project the existing prepared picking triangles through the same camera and static ancestor matrices. They reuse that result for label planning and publication, with no layout reads or new geometry/assets. Bodies without a static picking mesh retain their sphere bound. Small-screen typography changes text size without scaling its positioning transform. Distant nebula banks fade out in body close-ups; attached shells and a selected nebula remain eligible.

World caption measurements are demand-driven: the existing worker planner requests bounds only for labels that pass its naming policy. The publisher reads those CSS bounds before writes, caches them, and requests a follow-up plan. Hidden and occluded captions do not force startup layout reads. Font or viewport invalidation retains the same eligibility policy.

On a query-specific reload, the search toolbar and category pills use the same pending-shell visibility rule as the sheet, dataset rail and footer. They reveal together after the requested view is restored.

## Startup reveal

A saved camera may have no matching baked billboard. While it prepares, the viewport uses a separate opaque cover with its own compositing layer. The world itself stays at its final opacity while the existing activation groups publish textures. The shared scene-ready publication removes the cover and reveals the sheet, search and pills together. Default startup and fly-to continue using their prepared billboard.
