Choose A if behavior stability outweighs early visual discovery. Existing planet scenes stay usable through facades; their completion gates deletion.

Choose B if the main uncertainty is whether prepared CSS imagery can look good enough. The prototype is evidence, not a second production engine.

C · Migrate while building the Milky Way

Agree the shared seam first: frame-aware camera state, supported capabilities, prepared-asset readiness and teardown. Keep old exports and data versions working while the two efforts progress.

The architecture all three paths should reach

Keep four packages. Engine receives numeric navigation targets; it does not import object recipes. Extend capabilities for fields and prepared view banks without forcing galaxies into the current surface recipe.

What changes as we leave the solar system

This is a representation progression, not five simultaneous detailed scenes. Galaxy-exterior quality can be proven while local details migrate. Free travel through a cloud or galaxy interior remains a separate rendering proof.

How the Milky Way could actually be built

Start with eight exterior views on one declared orbit, eight unsampled midpoints, camera reversal and a lateral move at the closest allowed distance. This is a bounded proof, not arbitrary travel through a volume.

Billboarding is a family of choices

Recommendation: validate a multiview exterior bank against the single-image baseline. Add depth layers only when the required camera movement needs them and measurements show they help. Interior traversal is a separate proof.
